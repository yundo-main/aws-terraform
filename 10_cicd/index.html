STEP 10 · CI/CD · PIPELINE

CI/CD — AWS 네이티브 파이프라인

S3 backend + DynamoDB — CI 환경에서 필수인 원격 state·잠금CodeCommit — git 소스 저장소 (push = 파이프라인 트리거)CodeBuild — terraform 설치 → init → validate → plan → apply 실행CodePipeline — 단계 오케스트레이션 + artifact 전달 + 수동 승인 게이트EventBridge — push 감지 규칙 (PollForSourceChanges=false면 자동 생성)
개요 — STEP 10 학습 내용

이론적 배경

로컬 terraform apply는 개발자 PC에서 state를 만지지만, 팀·자동화 환경에서는 state를 S3 backend에 두고 DynamoDB로 잠급니다. 파이프라인의 CodeBuild는 이 S3 state를 읽어 plan→apply합니다. plan과 apply 사이에 수동 승인을 둬서 "계획 확인 없이 인프라가 바뀌는" 사고를 막습니다.

학습 목표

  • AWS 네이티브 CI/CD 서비스(CodeCommit·CodeBuild·CodePipeline)의 역할을 안다
  • Terraform을 CI/CD에 올릴 때 필요한 S3 backend·DynamoDB lock을 설명할 수 있다
  • buildspec.yml의 phases 구조를 읽을 수 있다
  • plan→승인→apply 게이트가 왜 필요한지 설명할 수 있다

핵심 내용

  • S3 backend + DynamoDB — CI 환경에서 필수인 원격 state·잠금
  • CodeCommit — git 소스 저장소 (push = 파이프라인 트리거)
  • CodeBuild — terraform 설치 → init → validate → plan → apply 실행
  • CodePipeline — 단계 오케스트레이션 + artifact 전달 + 수동 승인 게이트
  • EventBridge — push 감지 규칙 (PollForSourceChanges=false면 자동 생성)

이 파이프라인의 범위

이 단계가 만드는 것은 인프라 파이프라인입니다 — .tf 코드 변경을 자동 배포합니다.

애플리케이션 배포는 별도 파이프라인입니다:

[인프라 파이프라인]  ← 이 디렉터리가 만드는 것
.tf push → plan → 승인 → apply   (VPC·EKS·RDS 같은 뼈대)

[앱 파이프라인]      ← 별도로 필요한 것 (확장 과제)
앱 코드 push → docker build → ECR push → EKS/EC2 배포
앱 파이프라인 구성 요소AWS 서비스
이미지 빌드 → ECR pushCodeBuild + ECR
EKS 배포CodeBuild에서 kubectl apply (또는 helm)
EC2 배포CodeDeploy (blue/green)
실패 복귀kubectl rollout undo / CodeDeploy 자동 롤백
결과 알림SNS / EventBridge

앱 배포 파이프라인 (app-pipeline.tf)

앱 소스 push → 이미지 빌드 → EKS 배포까지 구성된 두 번째 파이프라인:

앱 리포 push → [Build] CodeBuild(docker build → ECR push)
            → [Deploy] CodeBuild(kubectl apply + set image)
리소스역할
aws_ecr_repository.app앱 이미지 저장소
aws_codecommit_repository.app앱 소스 리포 (app/ 디렉터리 샘플 포함)

app_deploy 프로젝트kubectl apply + set image + rollout status 대기
imageDetail.json빌드→배포 간 이미지 URI 전달 artifact

실습 시나리오

장면: 수동 terraform apply로 관리하던 03_real 인프라를 GitOps로 전환 — push만으로 배포되는 구조를 직접 경험합니다.

준비 — 파이프라인 인프라 생성

cd step1_backend && terraform init && terraform apply
cd ../step2_infra_pipeline && terraform init && terraform apply
terraform output backend_snippet    # 03_real용 backend 설정 복사

장면 1 — 로컬 state → S3 backend 전환

  1. 03_real/versions.tf의 terraform {} 블록에 backend_snippet 붙여넣기
  2. cd ../../03_real && terraform init -migrate-state → yes
  3. terraform state list — S3에서 읽히는지 확인, S3 콘솔에서 state 파일 확인

장면 2 — 첫 파이프라인 실행

git remote add cicd <step2의 repo_clone_http>
git push cicd main
  • CodePipeline 콘솔에서 Source → Plan 단계가 초록→파랑으로 진행
  • Plan 완료 후 Approve에서 파이프라인이 멈춥니다 — 승인 없이는 인프라가 안 바뀜

장면 3 — 승인 게이트 경험

  1. Plan 단계 로그(CodeBuild)에서 Plan: 0 to add 확인
  2. Approve의 승인 버튼 클릭 → Apply 실행 → 완료

장면 4 — 실제 변경 배포

  1. 03_real/main.tf에서 태그 하나 수정 (예: default_tags에 Env = "cicd" 추가)
  2. git commit -am "add env tag" && git push cicd main
  3. 파이프라인이 자동으로 다시 시작 → Plan 로그에 실제 diff 표시
  4. 로그를 읽고 승인 → apply 완료 → AWS에서 태그 확인

장면 5 — 실패 경험 (의도적 오류)

  1. 03_real에 문법 오류를 넣고 push (예: 중괄호 하나 삭제)
  2. Plan 단계가 빨갛게 실패 — 파이프라인이 잘못된 코드를 차단
  3. 로그에서 에러 확인 → 고쳐서 push → 정상 통과 확인

선택 — 앱 파이프라인 (EKS 필요)

step3 apply + aws-auth 등록 후, 앱 리포에 샘플 push → 이미지 빌드→EKS 배포 확인.

파이프라인 테스트 — "CI/CD가 동작한다"는 뭘 확인하는가

apply가 된 것과 파이프라인이 동작하는 것은 다른 문제입니다. 아래 항목을 순서대로 검증합니다.

테스트 ① 트리거 — push가 파이프라인을 시작시키는가

echo "# test" >> ../../03_real/main.tf && git commit -am "ci test" && git push cicd main
  • 확인: CodePipeline 콘솔에서 새 실행이 시작됨 — CodeBuild를 수동 실행하지 않았는데 시작됐다면 EventBridge 감지 성공
  • 실패 시: 리모트 URL 오타 → terraform output repo_clone_http로 교정 / CodeCommit 미지원 계정이면 리포 생성 단계에서 이미 실패했어야 함

테스트 ② 각 단계가 순서대로 성공하는가

단계확인할 것성공 기준
SourceSourceArtifact가 artifact 버킷에 저장됨단계 초록
PlanCodeBuild 로그에 terraform plan 출력"Plan: N to add" 로그
Approve실행이 멈춤콘솔에 승인 버튼 대기 — 파이프라인이 알아서 안 넘어감
Applyterraform apply tfplan 로그plan 결과와 동일하게 적용

테스트 ③ 승인 게이트가 실제로 막는가

  • Plan까지 성공 후 승인을 안 누름 → Apply가 실행되지 않는 걸 확인 (게이트 동작 증명)
  • 승인 누르기 전 Plan 로그의 변경 내용 읽기 — 승인 = "이 plan을 승인"임을 체감

테스트 ④ 거부 — 잘못된 코드를 차단하는가

# 일부러 문법 오류 넣고 push
sed -i '' 's/cidr_block = /cidr_block == /' ../../03_real/main.tf
git commit -am "broken" && git push cicd main
# → Plan 단계 빨간색 → 파이프라인 멈춤 → 되돌리고 재push
  • 이게 CI/CD의 핵심 가치: 로컬이었다면 에러가 "내 터미널"에서 끝나지만, 파이프라인에서는 "배포가 차단"됩니다.

테스트 ⑤ 상태 정합 — 파이프라인 apply 후 state가 갱신됐는가

cd ../../03_real && terraform plan   # 로컬에서 확인
# → "No changes"가 나와야 함 — CodeBuild가 S3 state를 갱신했기 때문
# drift가 뜨면 state가 제대로 동기화 안 된 것

테스트 ⑥ 앱 파이프라인 (step3 — 선택)

# app/index.html 수정 → push → Build(docker)·Deploy(kubectl) 로그 확인
kubectl get pods -l app=sample-app -w   # 새 pod 롤링 확인
kubectl rollout status deployment/sample-app
  • 이미지 태그 = 커밋 해시 앞 8자리 — kubectl describe deploy로 태그가 새 값인지 확인하면 "내 push가 배포됐다"가 증명됩니다.

정리

cd step3_app_pipeline && terraform destroy   # 사용했다면
cd ../step2_infra_pipeline && terraform destroy
cd ../step1_backend && terraform destroy     # tfstate 버킷은 prevent_destroy로 보호됨

주의사항

  • CodeCommit은 신규 AWS 고객에게 제공이 제한될 수 있습니다 — 생성 실패 시 S3 소스 방식으로 대체
  • CodeBuild는 빌드 시간만큼 과금 (소액), 수동 승인 대기는 무료
  • tfstate 버킷은 prevent_destroy — 삭제하려면 수동으로 라이프사이클 해제
  • CodeBuild 역할에 AdministratorAccess — 학습용 한정, 실무는 최소권한으로 교체

산출물 · 완료 기준

  • git push 한 번으로 plan→승인→apply가 돌아가는 파이프라인
  • 원격 state(S3+DynamoDB) 구조 이해
  • [ ] 파이프라인 4단계(Source·Plan·Approve·Apply)의 역할을 설명할 수 있다
  • [ ] 로컬 state와 S3 backend의 차이를 안다
  • [ ] buildspec의 install/build/artifacts를 읽을 수 있다

# ============================================================
# 01-provider.tf — Terraform 코어·프로바이더 선언
# ============================================================

terraform {
  required_version = ">= 1.6.0, < 2.0.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = var.aws_region

  default_tags {
    tags = {
      Project   = "aws-tf"
      Stage     = "10_cicd"
      ManagedBy = "terraform"
    }
  }
}

# 호출자 정보 — 계정 ID 참조용
data "aws_caller_identity" "current" {}

# ---------- Terraform state backend (03_real이 사용) ----------
# S3 버킷 — state·artifact 저장소
resource "aws_s3_bucket" "tfstate" {
  bucket = "${var.project_name}-tfstate-${data.aws_caller_identity.current.account_id}"
  # destroy 금지 장치: state가 들어있는 버킷은 실수로 지우면 안 됨
  lifecycle {
    prevent_destroy = true
  }
}

# 버저닝 — state 실수 덮어쓰기 복구용
resource "aws_s3_bucket_versioning" "tfstate" {
  bucket = aws_s3_bucket.tfstate.id
  versioning_configuration { status = "Enabled" } # state 이력 복구용
}

# SSE — 저장 데이터 암호화
resource "aws_s3_bucket_server_side_encryption_configuration" "tfstate" {
  bucket = aws_s3_bucket.tfstate.id
  rule {
    apply_server_side_encryption_by_default { sse_algorithm = "AES256" }
  }
}

# 퍼블릭 차단 — state는 절대 공개 금지
resource "aws_s3_bucket_public_access_block" "tfstate" {
  bucket                  = aws_s3_bucket.tfstate.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

# DynamoDB lock — 동시 apply 방지 잠금 테이블
resource "aws_dynamodb_table" "tf_lock" {
  name         = "${var.project_name}-tf-lock"
  billing_mode = "PAY_PER_REQUEST" # state lock 전용 — 사용량 거의 없음
  hash_key     = "LockID"

  attribute {
    name = "LockID"
    type = "S"
  }
}

# CodeBuild — 앱 이미지 빌드 + ECR push
# 출력: imageDetail.json (다음 단계가 읽을 이미지 URI)
version: 0.2

phases:
  pre_build:
    commands:
      - aws ecr get-login-password --region $AWS_DEFAULT_REGION | docker login --username AWS --password-stdin $ECR_URI
      - TAG=${CODEBUILD_RESOLVED_SOURCE_VERSION:0:8}   # 커밋 해시 앞 8자리를 이미지 태그로
      - echo "build tag: $TAG"
  build:
    commands:
      - cd "$APP_DIR"
      - docker build -t "$ECR_URI:$TAG" .
  post_build:
    commands:
      - docker push "$ECR_URI:$TAG"
      - printf '{"image":"%s:%s"}' "$ECR_URI" "$TAG" > imageDetail.json
artifacts:
  files:
    - imageDetail.json
    - '10_cicd/app/deployment.yaml'

# CodeBuild — EKS 배포 단계
# imageDetail.json의 이미지 태그로 deployment 이미지를 교체
version: 0.2

phases:
  install:
    commands:
      - curl -fsSL -o kubectl "https://dl.k8s.io/release/v1.32.0/bin/linux/amd64/kubectl"
      - install -m 0755 kubectl /usr/local/bin/kubectl && kubectl version --client
  build:
    commands:
      - aws eks update-kubeconfig --name "$EKS_CLUSTER_NAME" --region "$AWS_DEFAULT_REGION"
      - IMAGE=$(grep -o '"image":"[^"]*"' imageDetail.json | cut -d'"' -f4)
      - echo "deploy image: $IMAGE"
      - kubectl apply -f 10_cicd/app/deployment.yaml
      - kubectl set image "deployment/$APP_NAME" "$APP_NAME=$IMAGE"
      - kubectl rollout status "deployment/$APP_NAME" --timeout=120s

# ---------- CodePipeline: 앱 배포 ----------
# CodePipeline — 단계 오케스트레이션
resource "aws_codepipeline" "app" {
  name     = "${var.project_name}-app-pipeline"
  role_arn = local.pipeline_role_arn # step2의 공용 역할

  artifact_store {
    location = local.artifacts_bucket
    type     = "S3"
  }

  stage {
    name = "Source"
    action {
      name             = "AppSource"
      category         = "Source"
      owner            = "AWS"
      provider         = "CodeCommit"
      version          = "1"
      output_artifacts = ["app_source"]
      configuration = {
        RepositoryName       = aws_codecommit_repository.app.repository_name
        BranchName           = var.repo_branch
        PollForSourceChanges = "false"
      }
    }
  }

  stage {
    name = "Build"
    action {
      name             = "DockerBuild"
      category         = "Build"
      owner            = "AWS"
      provider         = "CodeBuild"
      version          = "1"
      input_artifacts  = ["app_source"]
      output_artifacts = ["image_out"] # imageDetail.json — 다음 단계가 읽을 이미지 태그
      configuration = {
        ProjectName = aws_codebuild_project.app_build.name
      }
    }
  }

  stage {
    name = "Deploy"
    action {
      name            = "DeployEKS"
      category        = "Build"
      owner           = "AWS"
      provider        = "CodeBuild"
      version         = "1"
      input_artifacts = ["image_out"]
      configuration = {
        ProjectName = aws_codebuild_project.app_deploy.name
      }
    }
  }
}

      output_artifacts = ["source_out"]
      configuration = {
        RepositoryName       = aws_codecommit_repository.src.repository_name
        BranchName           = var.repo_branch
        PollForSourceChanges = "false" # EventBridge 규칙이 자동 생성돼 push 감지
      }
    }
  }

  stage {
    name = "Plan"
    action {
      name             = "TerraformPlan"
      category         = "Build"
      owner            = "AWS"
      provider         = "CodeBuild"
      version          = "1"
      input_artifacts  = ["source_out"]
      output_artifacts = ["plan_out"] # tfplan 파일을 다음 단계로 전달
      configuration = {
        ProjectName = aws_codebuild_project.plan.name
      }
    }
  }

  stage {
    name = "Approve"
    action {
      name      = "ManualApproval"
      category  = "Approval"
      owner     = "AWS"
      provider  = "Manual"
      version   = "1"
      run_order = 1
      # 콘솔에서 plan 로그 확인 후 승인 버튼
      configuration = {
        CustomData = "Plan 로그를 확인한 뒤 승인하세요"
      }
    }
  }

  stage {
    name = "Apply"
    action {
      name            = "TerraformApply"
      category        = "Build"
      owner           = "AWS"
      provider        = "CodeBuild"
      version         = "1"
      input_artifacts = ["plan_out"] # plan 결과물 그대로 적용
      configuration = {
        ProjectName = aws_codebuild_project.apply.name
      }
    }
  }
}
