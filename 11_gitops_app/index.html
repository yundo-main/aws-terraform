개요 — STEP 11 학습 내용

리포 구조 — 리포 1개, 브랜치 2개

yundo-main/aws-terraform  (GitHub 리포 하나)
├── main 브랜치  → 10_gitops_infra 인프라 파이프라인 트리거 (운영)
└── dev  브랜치  → 11_gitops_app 앱 파이프라인 트리거 (개발)

CodeCommit·별도 리포 없이 평소 하던 git push만으로 두 파이프라인이 각자의 브랜치를 감시합니다.

만드는 리소스 (5개)

리소스역할
aws_ecr_repository.app앱 이미지 저장소
aws_codebuild_project.app_buildprivileged_mode docker build → ECR push
aws_codebuild_project.app_deploykubectl apply + set image + rollout 대기
aws_codepipeline.appSource→Build→Deploy 3단계 — 소스는 10의 connection 공용
(10의 connection·IAM 역할 재사용)별도 연결 생성 없음 — remote_state로 참조

핵심 포인트

  • local.*은 10_gitops_infra의 출력입니다 — connection·역할·버킷을 새로 안 만듭니다.
  • imageDetail.json이 빌드→배포 간 이미지 URI를 전달하는 artifact입니다.
  • buildspec은 리포 안 경로(11_gitops_app/buildspec-app-*.yml)로 참조 — 소스가 모노리포라 그대로 동작합니다.
  • 이미지 태그 = 커밋 해시 앞 8자리 — "어느 커밋이 배포됐는가"가 태그에 박힙니다.

---

실습 절차 — Step 0부터 Step 8까지

장면: dev 브랜치에 push하면 샘플 앱이 자동으로 빌드·배포되는 파이프라인을 만듭니다.

모든 git 명령은 리포 루트에서 실행합니다.

Step 0 — 전제 확인 (4가지 모두 충족해야 진행)

# 리포 루트에서
cd 10_gitops_infra && terraform output codebuild_role_arn     # ① 10이 apply된 상태
aws codeconnections list-connections \
  --query 'Connections[*].[ConnectionName,ConnectionStatus]' --output table
# ② <project>-github  AVAILABLE
aws eks list-clusters --region ap-northeast-2                 # ③ EKS 클러스터 존재
kubectl get nodes                                             # ④ kubectl이 클러스터에 닿음
  • ① 없으면 → cd 10_gitops_infra && terraform apply 먼저
  • ③ 없으면 → cd 03_real && terraform apply로 EKS 생성, 또는 eks_cluster_name 변수를 살아있는 클러스터로

Step 1 — 앱 파이프라인 생성

cd 11_gitops_app
terraform init        # remote_state로 ../10_gitops_infra를 읽음
terraform apply       # → 5 to add (ECR + CodeBuild×2 + Pipeline + ECR policy)

확인: terraform output — ECR 리포 URL·파이프라인 이름.

자주 나는 오류: Error reading remote state → 10이 apply 안 됐거나 terraform.tfstate가 없음.

Step 2 — aws-auth 등록 (수동 1회, 필수)

CodeBuild 역할이 kubectl을 쓰려면 EKS의 aws-auth ConfigMap에 등록돼야 합니다 — 안 하면 Deploy 단계에서

Unauthorized로 실패합니다.

ROLE_ARN=$(cd 10_gitops_infra && terraform output -raw codebuild_role_arn)
echo $ROLE_ARN   # 예: arn:aws:iam::<acct>:role/<project>-codebuild

kubectl edit configmap aws-auth -n kube-system
# mapRoles: 아래에 추가
#   - rolearn: <위의 $ROLE_ARN>
#     username: codebuild
#     groups: ["system:masters"]

확인: kubectl get configmap aws-auth -n kube-system -o yaml | grep codebuild → rolearn이 보여야 함.

Step 3 — dev 브랜치 생성 (최초 1회)

git push origin main:dev    # 현재 main 내용으로 dev 브랜치 생성

이 한 번으로 GitHub에 dev가 생기고, 앱 파이프라인이 dev 브랜치 감시를 시작합니다.

Step 4 — 첫 배포 관찰

# 앱 코드에 작은 변경 — 예: index.html 한 줄 수정
cd 11_gitops_app/app
echo "<!-- v1 -->" >> index.html
git commit -am "app v1" && git push origin main:dev

관찰 — CodePipeline 콘솔 → 앱 파이프라인의 3단계 로그:

단계로그에서 보이는 것의미
Sourcedev 브랜치 소스 다운로드webhook 트리거 동작
Builddocker build → build tag: <커밋8> → ECR push이미지 생성·태그 부여
Deploydeploy image: <uri> → set image → rollout statusEKS에 새 버전 적용

승인 게이트는 없습니다 — 개발 파이프라인은 push 후 자동으로 끝까지 갑니다 (운영과의 비대칭이 표준).

Step 5 — 배포 검증

# 이미지가 ECR에 올라갔는지
aws ecr describe-images --repository-name <ecr-repo명> \
  --query 'imageDetails[*].imageTags' --output table

# EKS에 rollout됐는지
kubectl rollout status deployment/sample-app
kubectl get pods -l app=sample-app
kubectl describe deploy sample-app | grep Image:    # 태그 = 커밋 8자리인가

# 실제 동작 확인
kubectl port-forward svc/sample-app 8080:80 &
curl localhost:8080     # index.html 내용이 보이면 끝

Image:에 커밋 해시 태그가 보이면 "내 push가 배포됐다"의 증명이 완성됩니다.

Step 6 — 변경 배포 (두 번째 사이클)

# index.html의 본문을 바꾸고 다시 dev로 push
git commit -am "app v2" && git push origin main:dev
  • Build 로그에서 새 태그(새 커밋 8자리) 확인
  • kubectl get pods -w — 옛 pod가 Terminating → 새 pod가 Running으로 바뀌는 롤링 확인
  • curl localhost:8080으로 바뀐 내용 확인

Step 7 — 롤백 체험

kubectl rollout undo deployment/sample-app      # 이전 리비전으로 즉시 복귀
kubectl rollout status deployment/sample-app
kubectl describe deploy sample-app | grep Image:   # 태그가 이전 커밋으로 되돌아감

배포 파이프라인이 있어도 수동 롤백은 언제나 가능합니다 — rollout undo가 비상구입니다.

(파이프라인식 복구는 "되돌린 코드를 다시 dev에 push" = revert commit)

Step 8 — 정리

cd 11_gitops_app && terraform destroy    # ECR·빌드·파이프라인 삭제 (5개)
# 이후 10을 지울 땐 10_gitops_infra readme의 Step 8 참조

remote_state로 10을 참조하므로 11 → 10 순서가 정리 순서입니다 — 거꾸로 지우면 참조가 깨집니다.

테스트 요약

#테스트절차성공 기준
①dev 트리거git push origin main:dev앱 파이프라인만 시작 (인프라 파이프라인은 안 돔)
②브랜치 격리main에만 push앱 파이프라인 미동작 — 브랜치가 경계임을 증명
③빌드Build 로그 확인build tag: <커밋8> + ECR에 태그 존재
④배포describe deploy의 Image이미지 태그 = 방금 커밋 해시
⑤롤아웃get pods -w옛 pod 종료 → 새 pod 기동, 다운타임 없음

왜 브랜치로 나누는가

main에 push할 때마다 앱 이미지까지 재빌드되면 낭비입니다.

브랜치가 트리거 경계라, 인프라 변경은 main, 앱 변경은 dev로 흐름을 나눕니다 —

단일 리포의 단순함과 리포 분리의 격리 효과를 동시에 얻는 절충입니다.

리포 분리(실제 다른 리포)를 원하면 같은 connection으로 github_repo만 바꾸면 됩니다 — 구조는 같습니다.

주의사항

  • Deploy의 kubectl은 EKS 퍼블릭 엔드포인트로 접근 — 프라이빗 전용이면 별도 대책 필요
  • aws-auth 미등록이 Deploy 실패의 가장 흔한 원인 — Unauthorized 로그가 보이면 Step 2로
  • system:masters 권한은 학습용 — 실무는 네임스페이스 범위 Role로 제한
  • dev 브랜치가 없으면 파이프라인이 Source에서 실패 — Step 3 필수

산출물 · 완료 기준

  • dev 브랜치 push 한 번으로 docker build → ECR → EKS까지 자동 배포
  • "리포 하나·브랜치 둘" GitOps 패턴의 실전 경험
  • [ ] git push origin main:dev가 앱 파이프라인만 트리거함을 확인했다
  • [ ] imageDetail.json이 빌드→배포 계약임을 설명할 수 있다
  • [ ] aws-auth가 왜 필요한지 (IAM ≠ 클러스터 권한) 설명할 수 있다
  • [ ] 커밋 해시 태그로 "어느 코드가 배포됐는가"를 추적할 수 있다
  • [ ] kubectl rollout undo로 롤백할 수 있다

# ============================================================
# 00-remote-state.tf — 10_gitops_infra의 출력을 읽는 연결부
#   artifact 버킷·공용 역할·connection을 한 state에서 가져온다
# ============================================================

# remote_state — 다른 단계의 출력 읽기
data "terraform_remote_state" "cicd" {
  backend = "local"
  config = {
    path = "../10_gitops_infra/terraform.tfstate"
  }
}

locals {
  artifacts_bucket   = data.terraform_remote_state.cicd.outputs.artifacts_bucket
  codebuild_role_arn = data.terraform_remote_state.cicd.outputs.codebuild_role_arn
  pipeline_role_arn  = data.terraform_remote_state.cicd.outputs.pipeline_role_arn
  pipeline_role_name = data.terraform_remote_state.cicd.outputs.pipeline_role_name
  connection_arn     = data.terraform_remote_state.cicd.outputs.github_connection_arn
}

terraform {
  required_version = ">= 1.6.0, < 2.0.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = var.aws_region

  default_tags {
    tags = {
      Project   = "aws-tf"
      Stage     = "11_gitops_app"
      ManagedBy = "terraform"
    }
  }
}

# ============================================================
# buildspec-app-build.yml — CodeBuild "build" 단계 실행 스크립트
#
# dev 브랜치 push로 시작되는 앱 파이프라인의 첫 작업:
#   docker build → ECR push → 다음 단계에 이미지 URI 전달
#
# docker 데몬을 쓰므로 프로젝트에 privileged_mode=true가 필요하다
# (11_gitops_app/main.tf의 aws_codebuild_project.build 참조).
#
# 주입되는 환경변수:
#   APP_DIR   샘플 앱 디렉터리 (기본 11_gitops_app/app — Dockerfile 위치)
#   ECR_URI   이미지를 push할 ECR 리포지토리 URI (태그 제외)
#   AWS_DEFAULT_REGION  CodeBuild 기본 제공 변수
# ============================================================
version: 0.2

phases:
  pre_build:
    commands:
      # ECR 로그인 — get-login-password가 내보낸 토큰을 docker login으로 파이프
      - aws ecr get-login-password --region $AWS_DEFAULT_REGION | docker login --username AWS --password-stdin $ECR_URI

      # 이미지 태그 = 소스 커밋 해시 앞 8자리.
      # CODEBUILD_RESOLVED_SOURCE_VERSION는 CodeBuild가 제공하는
      # 이번 빌드의 커밋 해시 — "어느 코드로 만든 이미지인지" 추적 가능
      - TAG=${CODEBUILD_RESOLVED_SOURCE_VERSION:0:8}
      - echo "build tag: $TAG"
  build:
    commands:
      # Dockerfile이 있는 앱 디렉터리로 이동해 이미지 빌드
      - cd "$APP_DIR"
      - docker build -t "$ECR_URI:$TAG" .
  post_build:
    commands:
      # ECR에 push — Deploy 단계가 같은 태그를 pull해 배포한다
      - docker push "$ECR_URI:$TAG"

      # 빌드 → 배포 계약: imageDetail.json에 이미지 URI를 적어둔다.
      # tfplan과 같은 패턴 — "빌드한 것과 배포하는 것이 일치함"을 보장
      - printf '{"image":"%s:%s"}' "$ECR_URI" "$TAG" > imageDetail.json

artifacts:
  files:
    # Deploy 단계가 읽는 두 파일:
    - imageDetail.json                       # 방금 빌드한 이미지 URI
    - '11_gitops_app/app/deployment.yaml'  # EKS에 적용할 매니페스트

# ============================================================
# buildspec-app-deploy.yml — CodeBuild "deploy" 단계 실행 스크립트
#
# Build 단계 artifact(imageDetail.json + deployment.yaml)를 입력으로 받아
# EKS 클러스터에 방금 빌드한 이미지를 배포한다.
#
# 주입되는 환경변수:
#   EKS_CLUSTER_NAME  배포 대상 EKS 클러스터 이름
#   APP_NAME          deployment·컨테이너 이름 (deployment.yaml과 일치해야 함)
#   AWS_DEFAULT_REGION  CodeBuild 기본 제공 변수
#
# 이 빌드의 CodeBuild 역할은 EKS를 조작할 권한이 있어야 한다 —
# EKS 쪽에서는 aws-auth ConfigMap(또는 access entry)으로
# 해당 IAM 역할에 클러스터 권한을 매핑해 두어야 kubectl이 허용된다.
# ============================================================
version: 0.2

phases:
  install:
    commands:
      # kubectl 설치 — CodeBuild 이미지에는 없어서 매번 내려받는다
      - curl -fsSL -o kubectl "https://dl.k8s.io/release/v1.32.0/bin/linux/amd64/kubectl"
      - install -m 0755 kubectl /usr/local/bin/kubectl && kubectl version --client
  build:
    commands:
      # 이 빌드 컨테이너의 kubeconfig를 대상 클러스터로 설정
      - aws eks update-kubeconfig --name "$EKS_CLUSTER_NAME" --region "$AWS_DEFAULT_REGION"

      # build 단계가 적어둔 이미지 URI를 읽는다 — 재계산 없이 그대로 사용
      - IMAGE=$(grep -o '"image":"[^"]*"' imageDetail.json | cut -d'"' -f4)
      - echo "deploy image: $IMAGE"

      # 매니페스트 첫 적용 — deployment·service가 없으면 생성, 있으면 갱신
      - kubectl apply -f 11_gitops_app/app/deployment.yaml

      # deployment의 컨테이너 이미지를 방금 빌드한 태그로 교체 → rollout 시작
      - kubectl set image "deployment/$APP_NAME" "$APP_NAME=$IMAGE"

      # rollout 완료까지 대기 — 타임아웃 안에 안 끝나면 빌드 실패로 간주.
      # "시작시켰다"가 아니라 "실제로 배포됐다"를 파이프라인 결과로 보고하기 위함
      - kubectl rollout status "deployment/$APP_NAME" --timeout=120s

#   앱 코드 push → docker build → ECR push → EKS 배포

# ---------- 이미지 저장소 ----------
# ECR — 앱 이미지 저장소
resource "aws_ecr_repository" "app" {
  name         = var.app_name
  force_delete = true # 실습용 — 이미지 있어도 삭제 가능
}

# ---------- CodeBuild: docker build ----------
# CodeBuild — plan/apply 실행 환경
resource "aws_codebuild_project" "app_build" {
  name         = "${var.project_name}-app-build"
  service_role = local.codebuild_role_arn # 10_gitops_infra의 공용 역할

  source {
    type      = "CODEPIPELINE"
    buildspec = "11_gitops_app/buildspec-app-build.yml"
  }
  artifacts { type = "CODEPIPELINE" }

  environment {
    compute_type    = "BUILD_GENERAL1_SMALL"
    image           = "aws/codebuild/standard:7.0"
    type            = "LINUX_CONTAINER"
    privileged_mode = true # docker 데몬 사용에 필수

    environment_variable {
      name  = "ECR_URI"
      value = aws_ecr_repository.app.repository_url
    }
    environment_variable {
      name  = "APP_DIR"
      value = "11_gitops_app/app"
    }
  }
}

# ---------- CodeBuild: EKS deploy ----------
# CodeBuild — plan/apply 실행 환경
resource "aws_codebuild_project" "app_deploy" {
  name         = "${var.project_name}-app-deploy"
  service_role = local.codebuild_role_arn

  source {
    type      = "CODEPIPELINE"
    buildspec = "11_gitops_app/buildspec-app-deploy.yml"
  }
  artifacts { type = "CODEPIPELINE" }

  environment {
    compute_type = "BUILD_GENERAL1_SMALL"
    image        = "aws/codebuild/standard:7.0"
    type         = "LINUX_CONTAINER"

    environment_variable {
      name  = "EKS_CLUSTER_NAME"
      value = var.eks_cluster_name
    }
    environment_variable {
      name  = "APP_NAME"
      value = var.app_name
    }
  }
}

# ---------- CodePipeline: 앱 배포 ----------
# CodePipeline — 단계 오케스트레이션
resource "aws_codepipeline" "app" {
  name     = "${var.project_name}-app-pipeline"
  role_arn = local.pipeline_role_arn # 10_gitops_infra의 공용 역할

  artifact_store {
    location = local.artifacts_bucket
    type     = "S3"
  }

  stage {
    name = "Source"
    action {
      name             = "AppSource"
      category         = "Source"
      owner            = "AWS"
      provider         = "CodeStarSourceConnection"
      version          = "1"
      output_artifacts = ["app_source"]
      configuration = {
        ConnectionArn        = local.connection_arn
        FullRepositoryId     = var.github_repo
        BranchName           = var.repo_branch
        OutputArtifactFormat = "CODE_ZIP"
        DetectChanges        = "true"
      }
    }
  }

  stage {
    name = "Build"
    action {
      name             = "DockerBuild"
      category         = "Build"
      owner            = "AWS"
      provider         = "CodeBuild"
      version          = "1"
      input_artifacts  = ["app_source"]
      output_artifacts = ["image_out"] # imageDetail.json — 다음 단계가 읽을 이미지 태그
      configuration = {
        ProjectName = aws_codebuild_project.app_build.name
      }
    }
  }

  stage {
    name = "Deploy"
    action {
      name            = "DeployEKS"
      category        = "Build"
      owner           = "AWS"
      provider        = "CodeBuild"
      version         = "1"
      input_artifacts = ["image_out"]
      configuration = {
        ProjectName = aws_codebuild_project.app_deploy.name
      }
    }
  }
}
